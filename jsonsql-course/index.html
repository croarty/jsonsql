From Question to Answer

What JsonSQL does, and what happens in the half-second after you press Enter

A search engine for your data files

Lots of software stores information in JSON files: long, nested text documents full of curly braces. They are easy for computers to write, but painful for humans to ask questions of. "Which products cost more than $20?" usually means writing a custom program.

JsonSQL lets you ask that question in SQL instead, straight from your terminal. No database to install, no setup of the data's shape ahead of time.

A JSON file
products, orders, customers, nested any way you like

→
2

SELECT name, price FROM products WHERE price > 20

→
3

An answer
clean JSON or a CSV you can open in Excel

Where it all begins: three lines

Every Java program has a starting point called main, the entry point. JsonSQL's is tiny, because it hands almost all the work to a helper library called Picocli.

JsonSqlCli.java 
    public static void main(String[] args) {        int exitCode = new CommandLine(new JsonSqlCli()).execute(args);        System.exit(exitCode);    }
PLAIN ENGLISH

"Start here." args is everything you typed after jsonsql, chopped into words.

Hand those words to Picocli. It matches each flag to a setting, then runs the tool and gets back a result number.

Quit, reporting that number to whoever launched us: 0 for "worked", 1 for "something went wrong".

Done.

How does Picocli know what --query means? Each flag is declared right next to the variable that will hold its value, using a label called an annotation:

JsonSqlCli.java 
    @Option(names = {"-q", "--query"}, description = "SQL query to execute")    private String query;
PLAIN ENGLISH

"This is a flag. Users may type -q or --query. Show this description in the help text."

Whatever text follows the flag gets stored in a variable named query.

💡
Declare, don't parse

Nobody wrote code to split your command into words and hunt for --query. The project just declares what flags exist, and a library does the tedious work. When you ask AI to "add a flag", the right answer here is one new @Option line, not a hand-written parser.

The handoff to the engine

Once the front door has checked your flags, it gathers the optional helpers (a cache, indexes, saved views), builds the engine, and asks it one question: execute(query).

JsonSqlCli.java 
                CacheManager cacheManager = enableCache ? new CacheManager(dataDirectory) : null;                IndexManager indexManager = noIndex ? null : loadIndexManagerQuietly();                MaterializedViewManager viewManager = loadViewManagerQuietly();                QueryExecutor executor = new QueryExecutor(mappingManager, dataDirectory, cacheManager,                    indexManager, viewManager);                if (dryRun) {                    System.out.println(DryRunReporter.format(executor.dryRunValidate(query), mappingManager));                    return 0;                }                result = executor.execute(query);
PLAIN ENGLISH

If you said --enable-cache, set up a cache. Otherwise use null, which means "nothing here".

Load any indexes, unless you said --no-index.

Load any saved "materialized views" (more on these in Module 4).

Build the engine, handing it the address book of tables, the data folder, and the optional helpers...

 

If you only asked for a --dry-run...

...just check the query is valid and print a report,

and stop without touching any data.

 

Otherwise, run the real thing and keep the result.

🔌
Optional helpers are plugged in, not baked in

The engine works fine with null for the cache, indexes and views. Each speed-up is an add-on you can switch off. That is why turning off caching can never change your answers, only how fast they arrive.

The address book: MappingManager

Think of the "saved places" in a maps app. You save "Home" once, and from then on you never type the full street address. A mapping does the same for data: the short name products stands in for "the list at this JSONPath, inside this file".

$.products Path only. Read it from products.json in the data folder.
orders.json:$.orders A specific file, then a path inside it.
products-multi:$.products A whole folder. Every .json file inside (even in sub-folders) is combined into one table.
C:\data\items.json:$.items A full Windows path. Note the extra colon after C.

That last one is a trap. If the code split the text at the first colon, C:\data... would be cut in half. Here is how the code avoids it:

MappingManager.java 
    private int filenameDelimiterIndex(String mapping) {        if (mapping == null || mapping.startsWith("$")) {            return -1;        }        int idx = mapping.indexOf(":$");        return idx > 0 ? idx : -1;    }
PLAIN ENGLISH

"Where does the file name end and the JSONPath begin?"

If the mapping starts with $, there is no file name at all...

...so answer -1, meaning "not found".

 

Otherwise, look for a colon immediately followed by a dollar sign. A drive letter like C:\ never matches that.

Return where that split point is, or -1 if there isn't one.

 

The translator: QueryParser

Remember diagramming sentences at school, labelling the subject, verb and object? That is what parsing is. JsonSQL hands your SQL to a library called JSqlParser, which builds a structured tree. QueryParser then copies the parts it cares about into its own simpler object, a ParsedQuery.

QueryParser.java 
        // Parse DISTINCT        if (plainSelect.getDistinct() != null) {            query.setDistinct(true);        }         // Parse SELECT clause        parseSelectItems(plainSelect, query);         // Parse FROM clause        parseFromClause(plainSelect, query);         // Parse JOINs        parseJoins(plainSelect, query);         // Parse WHERE clause        if (plainSelect.getWhere() != null) {            query.setWhereExpression(plainSelect.getWhere());        }
PLAIN ENGLISH

 

Did you write SELECT DISTINCT?

Then tick the "remove duplicates" box on our plan.

 

 

 

Write down which columns you asked for.

 

 

Write down which table you are reading from (and its nickname).

 

 

Write down any tables to join on.

 

 

If there is a WHERE condition...

...keep it as-is, still in tree form. The judge will read it later, row by row.

 

💡
Understanding is separate from doing

The parser never opens a file; the executor never reads raw SQL text. This split is called separation of concerns. It means a test can check "did we understand the SQL correctly?" without any data at all, and the --dry-run flag can validate a query without running it.

03

The Assembly Line

How the engine turns a pile of rows into your answer, one station at a time

Eight stations, always in the same order

Picture a car factory. The chassis rolls past welding, then painting, then wheels. You never paint before welding. QueryExecutor works the same way: every query rides the same conveyor belt, and each station does one job to the list of rows it receives.

1
Load

Open the backing JSON file(s), follow the mapping, collect the rows

2
UNNEST

Explode list fields (like tags) into one row per item

3
JOIN

Glue matching rows from other tables onto each row

4
WHERE

Throw away rows that fail the condition

5
ORDER BY

Sort the survivors

6
Project (SELECT list)

Keep only the columns you asked for

7
DISTINCT

Remove duplicate rows

8
LIMIT / TOP

Cut the list to the first N rows

The last five stations, in code

Each station takes a list and hands a (usually smaller) list to the next. Notice that the comments (grey lines starting with //) explain why the order matters.

QueryExecutor.java 
        // Apply WHERE clause        List<JsonNode> filteredData = joinedData;        if (parsedQuery.hasWhere()) {            filteredData = applyWhere(joinedData, parsedQuery.getWhereExpression());        }         // Apply ORDER BY before projection so sort keys not present in the SELECT list        // (e.g. ORDER BY id while selecting only name) remain available.        if (parsedQuery.hasOrderBy()) {            filteredData = applyOrderBy(filteredData, parsedQuery.getOrderBy());        }         // Project SELECT columns        List<JsonNode> projectedData = projectColumns(filteredData, parsedQuery.getSelectColumns());         // Apply DISTINCT after projection (dedupe the projected rows, preserving sorted order)        if (parsedQuery.isDistinct()) {            projectedData = applyDistinct(projectedData);        }         // Apply TOP/LIMIT last, so it operates on the final ordered/projected/deduped result set        if (parsedQuery.getEffectiveLimit() != null) {            int limit = parsedQuery.getEffectiveLimit().intValue();            projectedData = projectedData.subList(0, Math.min(limit, projectedData.size()));        }
PLAIN ENGLISH

WHERE: start by assuming every joined row survives.

If there is a condition, keep only the rows that pass it.

 

ORDER BY happens while rows still have all their fields. That way you can sort by price even if you only asked to see names.

 

Project: now cut each row down to just the columns in your SELECT list.

 

DISTINCT runs on the trimmed rows, because "duplicate" should mean "looks the same in your answer".

 

LIMIT comes dead last. Take the first N rows of the finished list, or all of them if there are fewer than N.

Luggage tags: how rows remember where they came from

When orders and products are joined, both have an id. Which is which? At the airport, every suitcase gets a tag before it joins the shared conveyor. The engine does the same: as each row is loaded, it is wrapped inside an outer object labelled with the table's alias (nickname).

QueryExecutor.java 
            // Wrap each row with table name for qualified column access            for (JsonNode node : fileData) {                if (node.isObject()) {                    ObjectNode wrappedNode = objectMapper.createObjectNode();                    wrappedNode.set(tableInfo.getEffectiveName(), (ObjectNode) node);                    dataList.add(wrappedNode);                } else {                    dataList.add(node);                }            }
PLAIN ENGLISH

 

Go through every row we read from this file.

If it is a proper record (curly braces)...

...make a new, empty outer envelope,

put the row inside it under the table's nickname, so {"id":7} becomes {"o": {"id":7}},

and add the envelope to our list.

Anything odd (not a record)...

...is passed along untouched.

 

 

Now o.id means "open envelope o, read id". If you write just id, the engine peeks inside each envelope until it finds one. And for SELECT *, the envelopes are unpacked again so you never see them.

JOIN: matching socks from two baskets

Emptying a laundry basket, you pick up one sock and compare it against every sock in the other basket. That is exactly how the join works: a nested loop.

QueryExecutor.java 
        for (JsonNode leftRow : leftData) {            boolean matchFound = false;             for (JsonNode rightRow : rightData) {                if (matchesJoinCondition(leftRow, rightRow, condition)) {                    // Merge left and right rows                    ObjectNode mergedRow = objectMapper.createObjectNode();                    mergedRow.setAll((ObjectNode) leftRow);                    mergedRow.setAll((ObjectNode) rightRow);                    result.add(mergedRow);                    matchFound = true;                }            }             // For LEFT JOIN, include left row even if no match found            if (joinInfo.isLeftJoin() && !matchFound) {                result.add(leftRow);            }        }
PLAIN ENGLISH

Pick up each order, one at a time.

So far, no partner found for it.

 

Compare it against every product.

Does this pair satisfy o.productId = p.id?

 

Yes: make a combined row containing...

...the order's envelope o...

...and the product's envelope p,

and keep it.

Remember this order found at least one match.

 

 

 

 

For a LEFT JOIN, an order with no matching product still gets kept, just without product details.

 

 

 

💡
Simple code, multiplying cost

1,000 orders × 1,000 products = 1,000,000 comparisons. 10,000 × 10,000 = 100 million. This "compare everything with everything" approach is easy to read and always correct, but slows down fast as data grows. Real databases use a hash join: build a lookup table of products by id once, then each order finds its match instantly.

The judge: a function that calls itself

A WHERE clause like (category = 'Tools' AND price > 10) OR inStock = true is stored as a tree: OR at the top, with an AND underneath. WhereEvaluator handles it with recursion: to judge an AND, it judges each half using itself.

WhereEvaluator.java 
        // Handle AND        if (expression instanceof AndExpression) {            AndExpression andExpr = (AndExpression) expression;            return evaluate(row, andExpr.getLeftExpression()) &&                    evaluate(row, andExpr.getRightExpression());        }                // Handle OR        if (expression instanceof OrExpression) {            OrExpression orExpr = (OrExpression) expression;            return evaluate(row, orExpr.getLeftExpression()) ||                    evaluate(row, orExpr.getRightExpression());        }
PLAIN ENGLISH

 

Is this piece of the tree an AND?

 

Then the row passes only if the left half passes and...

...the right half passes. If the left fails, Java does not even bother checking the right.

 

 

 

Is it an OR?

 

Then passing either half is enough...

...and if the left half passes, the right is skipped.

 

LIKE 'Lap%'Translated into a pattern where % means "anything" and _ means "any one character"
ILIKE 'lap%'Same, but lowercases both sides first, so "Laptop" matches
IN ('A','B')Passes if the value equals any item in the list
IS NULLPasses if the field is missing or explicitly null

Working Smarter, Not Harder

Three optional tricks that make repeat questions fast, and the rule that keeps them from ever giving wrong answers

The expensive part: reading the whole file

Before any filtering happens, every backing file is read into memory in one gulp. There is no streaming. Even LIMIT 1 loads everything first, because LIMIT is the last station on the belt.

QueryExecutor.java 
    private List<JsonNode> loadFromFile(File jsonFile, String jsonPathExpression) throws IOException {        // Read JSON file        String jsonContent = Files.readString(jsonFile.toPath());                // Apply JSONPath        Object result = JsonPath.using(jsonPathConfig).parse(jsonContent).read(jsonPathExpression);
PLAIN ENGLISH

"Load the rows from this file, using this mapping path."

 

Read the entire file into one giant piece of text.

 

 

Parse all of it, then walk the path (e.g. $.data.products) to find the list we want.

So the three speed-ups all attack the same cost from different angles:

🧊

Cache

Read the same file faster next time. --enable-cache

🔎

Index

Don't read files that can't contain a match. --add-index

🏛️

Materialized view

Save a heavy query's answer and reuse it as a table. --materialize-view

The cache: photocopies stamped with an edition number

Imagine photocopying a chapter so you don't have to fetch the heavy book again. The danger: the book gets a new edition and your copy is now wrong. JsonSQL's fix is to write the book's "edition" (its last-saved time and size) into the name of every copy. A cache entry for an old edition simply never gets asked for again.

CacheManager.java 
        long lastModified = jsonFile.lastModified();        long length = jsonFile.length();        try {            String absolutePath = jsonFile.getAbsolutePath();            // Combine file path, JSONPath, mtime and size for a freshness-sensitive cache key            String cacheKey = absolutePath + "|" + jsonPathExpression + "|" + lastModified + "|" + length;            String hash = hashPath(cacheKey);
PLAIN ENGLISH

When was this data file last saved?

How many bytes is it?

 

Where exactly is it on disk?

 

Glue together: location + which list inside it + save time + size. Change any one and you get a different cache key.

Squash that long label into a short fixed-length code (a hash) to use as the cache file's name.

💡
Put freshness in the key, not in a cleanup job

Programmers joke that cache invalidation (knowing when stored copies are out of date) is one of the two hardest problems in computing. Folding "what could change the answer" into the key side-steps it entirely. When you ask AI to cache something, ask: "what goes into the cache key?" If anything that affects the result is missing, you will get stale answers.

Indexes: reading the labels on the binders

Picture a shelf of binders, one per data file. Each spine has a sticky label: "contains categories: Tools, Office · prices 5 to 240". Looking for something over $500? You can skip that binder without opening it. JsonSQL's index builds exactly these labels, called file summaries.

Query: SELECT * FROM catalog WHERE category = 'Tools' AND price > 500 (illustrative summaries)

tools/2024.json · KEEP

categories: Tools
price: 12 to 899
Could hold a match, so it must be read.

tools/2021.json · SKIP

categories: Tools
price: 4 to 310
Max price 310 is not over 500. Nothing here can match.

office/2024.json · SKIP

categories: Office
price: 3 to 1,200
No "Tools" anywhere in it.

misc.json · KEEP

No fresh summary (file edited since the index was built). Can't prove anything, so read it.

Here is the check for a "greater than" style condition on numbers. It only needs the label's min and max:

IndexPlanner.java 
        if ("number".equals(type)) {            double v;            try {                v = Double.parseDouble(value);            } catch (NumberFormatException e) {                return true;            }            switch (op) {                case ">":  return max.asDouble() > v;                case ">=": return max.asDouble() >= v;                case "<":  return min.asDouble() < v;                case "<=": return min.asDouble() <= v;                default:   return true;            }        }
PLAIN ENGLISH

If this field holds numbers in this file...

 

try to read the query's value (e.g. 500) as a number.

 

If it isn't a number...

...answer "maybe it matches". Never skip on a guess.

 

Otherwise, depending on the comparison:

price > 500 can only match if the biggest price here is over 500.

Same idea for "at least".

price < 10 can only match if the smallest price here is under 10.

Same idea for "at most".

Anything unexpected: "maybe", keep the file.

 

 

The golden rule: when in doubt, read the file

Skipping a file that did contain a match would silently give you a wrong answer, which is far worse than a slow one. So the whole index system is wrapped in a safety net:

IndexPlanner.java 
    public List<File> prune(TableInfo fromTable, ParsedQuery query, List<File> currentFiles) {        try {            return doPrune(fromTable, query, currentFiles);        } catch (RuntimeException e) {            return currentFiles;        }    }
PLAIN ENGLISH

"Given these files, which ones do we actually need to read?"

Try the clever pruning logic...

...and return the shorter list if it works.

If anything goes wrong in there (an exception)...

...give back the full, original list. Slower, but always right.

 

 

✅
Can be used to skip files

Conditions every row must meet (joined by AND) using =, IN, >, >=, <, <=, backed by a fresh summary

🚫
Never used to skip

OR groups, NOT IN, LIKE, missing or stale summaries, a changed mapping. Other AND conditions can still help; if none are usable, every file is read.

Materialized views: the printed monthly report

Your finance team doesn't recompute last month's totals every time someone asks; they print a report, date it, and file it. A materialized view does that for a heavy CTE.

TERMINAL (from MATERIALIZED-VIEWS.md) 
jsonsql --materialize-view expensive \  --query "WITH expensive AS (SELECT id, category, price FROM catalog_large WHERE price > 100) SELECT * FROM expensive" \  --data-dir example-data # later, as if it were an ordinary table:jsonsql -q "SELECT id, category FROM expensive WHERE category = 'Electronics'" --data-dir example-data
PLAIN ENGLISH

"Save a report called expensive..."

"...made of every catalog item over $100." The rows are written to .jsonsql-views/expensive.json, and a fingerprint of the source files is recorded in .jsonsql-views.json.

 

 

 

Later queries read the small saved report instead of rescanning the whole catalog.

🗓️
Stale, but honest

If the source files change after the view was built, the view is marked STALE. It still returns the stored rows (that is the point of a saved report) but prints a warning telling you to run --rebuild-view. This is a deliberate trade-off between speed and freshness, and the tool tells you which one you are getting.

When Things Go Wrong

How JsonSQL reports trouble, the traps hiding in real data, and how to debug (and steer AI) without going in circles

Fail loudly, never quietly

A smoke alarm with a dead battery is worse than no alarm, because you trust it. Early on, a WHERE condition JsonSQL didn't understand (like BETWEEN) simply matched nothing, and you got an empty answer that looked real. Now the judge refuses to guess:

WhereEvaluator.java 
        // Unsupported expression type - fail loudly instead of silently excluding all rows        throw new UnsupportedExpressionException(            "Unsupported WHERE expression: " + expression +            " (type: " + expression.getClass().getSimpleName() + ")"        );
PLAIN ENGLISH

If we reach this line, none of the known operators matched.

Stop everything and raise an alarm...

...quoting the exact piece of SQL we did not understand...

...and what kind of thing the parser said it was (e.g. "Between"), which is a great clue for whoever adds support for it.

 

💡
A wrong answer that looks right is the worst bug there is

Crashes get noticed and fixed. Silently wrong results end up in reports. The same instinct runs through the whole codebase: JOIN rejects conditions it can't handle, LIMIT rejects negative numbers, and the index planner falls back to a full read when unsure. When reviewing AI code, watch for catch blocks that swallow errors and carry on with empty data.

The NULL trap

JSON records don't all have the same fields. Some products have no discount at all; some have "discount": null. SQL calls both NULL, and NULL fails every comparison, even "not equal to".

WhereEvaluator.java 
        // In SQL, any comparison with NULL returns NULL (treated as FALSE in WHERE clauses)        // This includes both missing fields (fieldValue == null) and present but null fields (fieldValue.isNull())        if (fieldValue == null || fieldValue.isNull()) {            return false;        }
PLAIN ENGLISH

Standard SQL rule: comparing with "no value" can never be true...

...whether the field is missing entirely or present but empty.

So if this row has no value for the field...

...the row fails, for =, !=, >, < alike.

 

🕳️

!= drops blanks

WHERE status != 'cancelled' also hides rows with no status. Add OR status IS NULL to keep them.

🔤

Numbers stored as text

"price": "9" (in quotes) is text, compared alphabetically. So "9" counts as greater than "10".

🔠

Field names are exact

Category and category are different fields. A typo means "missing", which means NULL, which means no rows.

💉

Parameters are pasted in

${category} is replaced with your text before parsing, with no escaping. Only use trusted values.

Two exits: one for answers, one for chatter

A building has a loading dock for deliveries and a reception desk for conversation. Command-line programs have the same two exits: stdout for results and stderr for everything else. JsonSQL is strict about this, so its output can be piped into other tools.

Your debugging toolkit

When a query misbehaves, resist the urge to have AI rewrite the engine. Work from the outside in, using flags the tool already gives you:

1
Read the error on stderr

It names the table, file or SQL fragment involved. Most problems end here.

2
--dry-run

Checks the SQL, the mappings and that the files exist, without loading data.

3
--describe products

Shows the real field names, their types and sample values. Catches typos and "numbers stored as text".

4
Remove the speed-ups

Add --no-index and drop --enable-cache. If the answer changes, you found a speed-up bug.

5
DEBUG=1

Prints the full stack trace for errors, the best thing to paste to an AI.

    static boolean isDebugEnabled() {        String debug = System.getenv("DEBUG");        if (debug == null) {            return false;        }        String v = debug.trim().toLowerCase();        return !(v.isEmpty() || v.equals("0") || v.equals("false") || v.equals("no") || v.equals("off"));    }
PLAIN ENGLISH

"Should we show the gory details?"

Look for a setting called DEBUG in the environment.

Not set at all?

Then no.

 

Tidy it up: trim spaces, ignore upper/lower case.

Anything except blank, 0, false, no or off counts as "yes", so DEBUG=false hides stack traces. (Real-world wrinkle: QueryExecutor's own "DEBUG:" lines only check whether DEBUG exists at all, so they still appear with DEBUG=false.)
